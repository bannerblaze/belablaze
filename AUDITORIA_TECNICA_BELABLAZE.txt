RESUMEN EJECUTIVO
================================================================================

BelaBlaze tiene una arquitectura bien pensada y relativamente madura para el
nivel de desarrollo en que está. El esqueleto es sólido: separación de capas
(actions → services → repositories → db), multi-tenancy por org-context,
auditoría en cada mutación, auth con Clerk v7. El player DOOH funciona de verdad.

Pero hay tres mentiras que el dashboard le dice al usuario que no debería:
las métricas de analytics son en parte fake, las impresiones están infladas 16x,
y "tiempo real" es polling disfrazado de SSE. Además faltan entre 6 y 8 features
completos para que un cliente de producción pueda usar el producto.

Estimación honesta de avance: 58–63% hacia un SaaS DOOH vendible.

--- Qué está bien diseñado ---

✅ Separación de capas — cada capa tiene responsabilidad clara
✅ Org-context validation — requireOrgContext() en TODA mutación;
   imposible cross-tenant leak por descuido
✅ Audit logging non-blocking — cada mutación loguea sin bloquear el flujo
✅ Player como ruta pública independiente — arquitectura correcta para TVs
   sin sesión
✅ Storage abstraction — storage.ts puede cambiar entre R2/Vercel Blob
   sin tocar el resto del código

--- Qué está improvisado o escalará mal ---

❌ getOrgContext() hace DB query en cada request — sin caché.
   Con 100+ usuarios concurrentes esto se convierte en N queries/segundo al DB.

❌ Analytics revenue calculado como impressions * 0.0015 hardcodeado
   (analytics.service.ts línea 122). No es billing real.

❌ HOUR_DATA en analytics UI generado con Math.sin() y valores hardcodeados
   (analytics/_client.tsx líneas 26-30). Es 100% fake.

❌ Fallback de ciudades — cuando no hay impresiones reales, usa traffic * 30
   como estimado (analytics.service.ts línea 190). Confunde al usuario.

❌ OrgRole enum en schema — existe pero no se usa en ningún código activo.
   Legacy muerto.

--- Riesgos futuros de la DB ---

1. Ad.impressions se incrementa desde el ping (cada 15s), no per-view.
   Dato corrupto desde el día 1 en producción.

2. revenue en getChartData() es impressions * 0.0015 — no viene de billing real.

3. Cuando no hay Metric rows, los gráficos quedan en cero aunque haya
   impresiones en Ad.impressions — dos contadores paralelos sin sincronizar.

4. Client.organizationId es nullable — si es null, ese cliente es "huérfano"
   y no aparece en queries org-scoped.

5. Queries de analytics (Metric → Ad → Campaign → org) son joins de 3 niveles
   sin índices verificados. Full table scans cuando la DB crezca.

--- Cómo fluye la data ---

[Usuario crea campaña]
  → campaigns.ts::createCampaign()
  → requireOrgContext() valida organización activa
  → db.campaign.create({ organizationId, ...formData })
  → logAuditEvent("CREATE", "CAMPAIGN", campaignId)
  → revalidatePath("/campaigns")

[Ad en producción]
  → TV abre /player/[playerKey]
  → page.tsx: getPlayerScreen(playerKey) + getActivePlaylist(screenId)
  → player.service.ts mezcla AdSchedule + ScreenCampaign items
  → DoohPlayer renderiza imagen/video
  → Cada 15s: POST /api/player/ping → actualiza Screen.lastPingAt + ONLINE
  → Cada 30s: GET /api/player/playlist/[playerKey] → refresca contenido

--- Problemas del player ---

🔴 CRÍTICO: Impressions infladas
   Cada ping (cada 15s) incrementa Ad.impressions si hay un ad activo.
   Un ad de 10 segundos en pantalla durante 4 minutos = 16 impresiones.
   Lo correcto sería contar 1 (una reproducción).

   Código del bug (src/app/api/player/ping/route.ts, líneas 57-61):
   if (currentAdId && typeof currentAdId === "string") {
     db.ad.updateMany({
       where: { id: currentAdId },
       data:  { impressions: { increment: 1 } },
     }).catch(() => {});
   }

⚠️ Sin WebSocket — playlist refresh es polling each 30s.
   Si un admin cambia la playlist, la TV lo ve en máximo 30s.
   Aceptable en producción pero no "tiempo real".

⚠️ Sin control remoto — no hay forma de pausar/reiniciar el player
   remotamente desde el dashboard.

⚠️ Sin logs de reproducción — no se registra qué ad se reprodujo,
   cuántas veces completo, ni si fue saltado por error.

--- Playlist logic en detalle ---

Dos fuentes de contenido (src/services/player.service.ts):

1. AdSchedule (getAdScheduleItems):
   - Ad específico → pantalla específica
   - Ventana horaria: daysOfWeek[], startTime "HH:MM", endTime "HH:MM"
   - Verifica: ad.status en PLAYABLE_AD_STATUSES, campaign.status en PLAYABLE_CAMPAIGN_STATUSES
   - NOTA: Campaign.startDate/endDate NO se verifica aquí (decisión de diseño)

2. ScreenCampaign (getScreenCampaignItems):
   - Campaña completa → pantalla, todos los ads activos de la campaña
   - Ventana de fechas: ScreenCampaign.startsAt/endsAt
   - Ordena por prioridad (priority: "desc")

Merge final:
   AdSchedule items primero → ScreenCampaign items después
   Deduplicación por adId usando Set → AdSchedule tiene precedencia

PLAYABLE_CAMPAIGN_STATUSES = ["ACTIVE", "APPROVED", "DRAFT"]
PLAYABLE_AD_STATUSES       = ["ACTIVE", "PUBLISHED", "APPROVED", "DRAFT"]

⚠️ NOTA: DRAFT campaigns y ads son reproducibles. Esto es intencional
   para facilitar pruebas, pero puede sorprender en producción.

--- Heartbeat (/api/player/ping) ---

Autenticación: playerKey (sin Clerk)
Body: { playerKey, currentAdId?, uptime?, resolution: {width, height} }

Side effects:
  • Screen.lastSeenAt = now
  • Screen.lastPingAt = now
  • Screen.status = "ONLINE"
  • Ad.impressions += 1 (si currentAdId presente) ← BUG

Respuesta: { ok: true, serverTime, uptimeAck, resolution }

6. MEDIA LIBRARY

--- Estado general ---

✅ Upload a R2 vía /api/media/upload con validación MIME y tamaño
✅ MediaAsset registrado en DB con storageKey, url, size, mimeType

--- Cómo funciona el upload ---

1. Cliente selecciona archivo
2. POST /api/media/upload con multipart/form-data
3. Valida MIME type contra lista permitida
4. Valida tamaño contra MAX_UPLOAD_BYTES
5. Upload a R2 usando @aws-sdk/lib-storage (multipart para archivos grandes)
6. Crea MediaAsset en DB con storageKey, url pública, size, mimeType
7. Retorna el MediaAsset creado

--- Problemas identificados ---

🔴 R2 no configurado — uploads fallan al arrancar si no hay env vars.
   El error no es amigable al usuario (throws en runtime, no en startup).

⚠️ Sin thumbnails de video — thumbnail column existe en schema, nadie
   la genera. Videos muestran blank en la media library grid.

⚠️ Sin límites de storage por org — UsageRecord existe en schema pero
   billing.ts no compara storageMB contra ningún límite.
   Cualquier org puede subir contenido ilimitado.

⚠️ @vercel/blob en código pero no instalado — si STORAGE_DRIVER=vercel,
   el servidor crashea con module not found.

⚠️ Sin presigned URLs — assets se sirven con URL pública directa de R2.
   No hay expiración ni control de acceso post-upload.

⚠️ Sin previews de video en la media library — solo imágenes tienen
   preview visual real.

7. ROLES Y AUTH
================================================================================

--- Tres capas de acceso ---

1. Clerk publicMetadata.role  (fuente de verdad para sesión, set by admin)
2. Prisma User.role           (DB, synced via webhook o auto-provision)
3. platform.ts PlatformRole   (SUPER_ADMIN / SUPPORT / USER)

--- Resolución de rol (src/lib/auth.ts) ---

Orden de precedencia:
  1. Clerk publicMetadata.role (admin-set)
  2. Clerk unsafeMetadata.role (user-writable, solo dev)
  3. Prisma User.role (DB source of truth)
  4. DEV fallback: "ADMIN" (nunca bloquea en development)
  5. PROD fallback: "CLIENT" (least privilege)

--- PlatformRole (src/lib/platform.ts) ---

SUPER_ADMIN:
  → Email en admin whitelist (admin@bannerblaze.com, ceo@bannerblaze.com,
    o ADMIN_WHITELIST_EMAILS env)
  → Bypasses ALL checks — puede acceder a datos de cualquier org
  → Modo "BannerBlaze staff ve todo"

SUPPORT:
  → accountType = INTERNAL (BannerBlaze staff sin godmode)

USER:
  → Todos los demás

⚠️ PROBLEMA: El check SUPER_ADMIN se hace cada request, sin caché.
   Requiere DB query + Clerk call por cada request de un admin.

--- AccountType (src/lib/access.ts) ---

ORGANIZATION: Superficie completa (campaigns, ads, screens, clients, audit,
              API keys, webhooks)
PERSON:       Superficie de creator (campaigns, ads, media only;
              sin clients/screens/audit/webhooks)
INTERNAL:     Staff de BannerBlaze (igual que ORGANIZATION)

--- Funciones de auth clave ---

getCurrentUser()       — Merge Clerk + Prisma. Auto-provisiona fila Prisma si no existe.
requireAuth()          — Redirect a /sign-in si no autenticado
requireAdmin()         — Throws AuthError si role ≠ ADMIN
requireAdminOrExecutive() — Throws AuthError si role ∉ {ADMIN, EXECUTIVE}
checkPermissions()     — Soft check: {isAdmin, isExecutive, isClient, canApprove, etc.}
requireOrgContext()    — Valida org activa, throws si no existe
requirePlatformAdmin() — Throws si no SUPER_ADMIN
requirePlatformStaff() — Throws si no SUPER_ADMIN | SUPPORT

--- Problemas de seguridad reales ---

🔴 CRÍTICO: CLERK_WEBHOOK_SECRET vacío
   El webhook en /api/webhooks/clerk verifica firma Svix.
   Con secret vacío, la verificación puede ser bypasseada.
   Cualquiera podría POST a /api/webhooks/clerk y crear/modificar
   usuarios en la DB sin autenticación real.

🟡 No hay middleware.ts:
   Sin rate limiting en edge.
   Sin logging de requests centralizado.
   Auth checks están en cada handler individualmente.
   Error handling varía entre handlers (algunos 401, otros throw, otros null).

🟠 /api/metrics solo verifica userId, no org-scope completo:
   route.ts línea 7: solo `if (!userId) return 401`
   La query interna usa getOrgContext() que sí está org-scoped, pero
   el check de entrada es inconsistente con el resto de la app.

⚠️ /settings/api-keys muestra "próxima versión" hardcodeado:
   Literal string en el componente: "La generación de claves estará
   disponible en la próxima versión."
   El usuario ve que la feature existe pero no puede usarla.

⚠️ /settings/webhooks — solo lectura, sin formulario de creación.
   Las tablas existen, la UI lee de DB, pero no hay forma de agregar.

--- Onboarding de admin (seguridad adicional) ---

El flujo de admin tiene dos gates:
  1. Email debe estar en ADMIN_WHITELIST_EMAILS
  2. Debe conocer ADMIN_ACCESS_CODE (BBZ_INTERNAL_X92_SECURE)

Rate limiting: SecurityLog con ventana de 15 minutos, máx 5 intentos.
Implementación: DB-backed (no Redis). Funciona pero es costoso a escala.

9. PERFORMANCE
================================================================================

--- Bottlenecks reales identificados ---

🔴 CRÍTICO: Impresiones infladas — analytics corrupto desde day 1
   Ad.impressions se incrementa con CADA heartbeat (cada 15s).
   Un anuncio de 30s que se reproduce 10 veces en una hora =
   240 impresiones contadas, no 10.
   El dashboard muestra este número. Los clientes verán métricas
   que no cuadran con la realidad.
   Corrección necesaria: contar 1 impresión por reproducción completa,
   no por heartbeat.

🟡 getOrgContext() sin caché en cada request
   Cada server component, action, y API handler necesita el org context:
     1. auth() → Clerk (JWT local en v7, pero puede ser network call)
     2. db.user.findUnique() → Neon (siempre network)
   Con 50 usuarios activos = ~100 queries/segundo al DB solo para
   resolver contexto.

🟡 Queries de analytics con joins de 3 niveles sin índices verificados
   Metric → Ad → Campaign → Organization
   Sin índices en Ad.campaignId o Campaign.organizationId,
   esto hace full table scans cuando la DB crece más allá de
   miles de registros.

🟠 Player polling — escala con número de pantallas
   Heartbeat cada 15s: UPDATE Screen SET lastSeenAt, lastPingAt, status
   Con 100 pantallas = 400 queries UPDATE/minuto solo por heartbeats.
   Playlist fetch cada 30s: 2 queries con JOINs por pantalla.
   Con 100 pantallas = 200 queries/minuto adicionales.

🟠 Revenue hardcodeado en analytics
   analytics.service.ts línea 122:
   revenue: (m._sum.impressions ?? 0) * 0.0015,
   Este número aparece en los gráficos. No es real.
   Es un CPM simulado ($0.0015 por impresión).

🟠 HOUR_DATA completamente fake en analytics UI
   analytics/_client.tsx líneas 26-30:
   const HOUR_DATA = Array.from({ length: 24 }, (_, h) => {
     const base = h >= 7 && h <= 22
       ? (h >= 11 && h <= 14 ? 120000 : h >= 17 && h <= 20 ? 150000 : 60000)
       : 8000;
     const jitter = Math.floor(Math.abs(Math.sin(h * 1.7 + 0.5)) * 18000);
     return { hour: `${h.toString().padStart(2, "0")}:00`, impressions: base + jitter };
   });
   Este array genera SIEMPRE los mismos datos (120K impresiones de 11am-2pm).
   No viene de la DB. Es marketing fictional presentado como analytics real.

🟠 City metrics fallback es estimado falso
   analytics.service.ts línea 189-190:
   if (cityData.every((c) => c.impressions === 0)) {
     return cityData.map((c) => ({ ...c, impressions: c.traffic * 30 }))
   }
   Cuando no hay impresiones reales, muestra traffic * 30 como estimado.
   Este número aparece igual que datos reales en la UI.

🟠 Fire-and-forget en impressions logging
   db.ad.updateMany(...).catch(() => {});
   Fallos son silenciosamente ignorados. Sin log de error.
   Dificulta debugging cuando las métricas no cuadran.

⚠️ Socket.io en package.json pero sin uso
   Añade ~100KB al bundle sin aportar funcionalidad.
